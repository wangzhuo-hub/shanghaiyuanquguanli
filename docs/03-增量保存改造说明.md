# 03 · 招商看板「增量保存 + 行级乐观锁」改造说明

> 本文档配套代码改造提交，描述新旧保存流程的差异、关键数据结构、前端调用规范、冲突处理流程，
> 以及灰度回滚方式。Owner：服务端 + 前端协作。

---

## 1 · 背景与动机

旧实现（`pocketbaseService.ts/saveToPocketBase`）的保存流程是：

> **删光该 `project_id` 下所有行 → 批量重建 → 写入全局 `dashboard_data_version` +1**

后果：
- 多人并发保存时，**后保存者会无声覆盖先保存者的全部改动**。
- 全局 `dashboard_data_version` 是行为锁，对「A 改租户 X、B 改租户 Y」这种本可以合并的场景也会被判为冲突，要求 B 放弃改动重新加载。

改造后：
- 前端按行登记 dirty（create/update/delete），保存时只提交真正改动的字段。
- 每行用 PocketBase 自带的 `updated` 字段做**行级乐观锁**。
- A、B 改不同行或不同字段，双方改动自动合并；只有改同一行才会触发冲突。
- 冲突由前端 `ConflictDialog` 让用户逐条决策（用我的 / 用服务端 / 跳过）。

## 2 · 新旧流程对比

### 旧流程（legacy）

```
用户编辑 → setState → 点保存
   │
   ▼
saveToCloud(data, config)
   │
   ▼
saveToPocketBase(data, projectId)
   │
   ├─ 读全局 dashboard_data_version → 不一致 → 拒绝保存（用户必须放弃改动）
   │
   ├─ 删光 project_id 下所有 pb_buildings / pb_units / pb_tenants ...
   │
   ├─ 批量重建所有行
   │
   └─ dashboard_data_version +1
```

### 新流程（incremental）

```
用户编辑 → setState → ALSO → dirtyTracker.markCreate/Update/Delete
   │                                            ▲
   │                                            │  baseUpdated 来自 recordMeta（加载时拍下的 updated 时间戳）
   ▼
点保存
   │
   ▼
runCloudSave(data, note)
   │
   ├─ SAVE_MODE === 'legacy'  ┐
   ├─ 或 tracker.isEmpty()    ├─→ saveToCloud（旧整包覆写，平滑迁移期回退）
   │                          ┘
   ▼
saveIncrementalToCloud(payload, config, recordMeta)
   │
   ├─ 对每个 create  → POST
   │
   ├─ 对每个 update  → 先 GET 目标行 → 比对 server.updated == baseUpdated
   │                                       │
   │                                       ├─ 一致：PATCH 仅改动字段
   │                                       └─ 不一致：写入 conflicts，不触动服务端
   │
   ├─ 对每个 delete  → 同上比对 → 一致才 DELETE
   │
   ▼
返回 { applied, conflicts, errors }
   │
   ├─ conflicts.length > 0 → 弹 ConflictDialog
   │                              │
   │                              └─ 用户决策 → forceOverwriteCloudRecord（用我的）/ 跳过 / 接受服务端
   │
   ▼
保存成功 → fetchCloudBackup 重拉 recordMeta + dirtyTracker.reset()
        → scheduleUpsertIntegrationFullSnapshot（OpenClaw 集成快照）
        → 可选 bumpCloudSaveVersion（仅审计，不再做前置校验）
```

## 3 · 关键数据结构

### 3.1 RecordMeta —— 行级乐观锁基准表

```ts
type RecordMeta = Record<string, Record<string, string>>;
//                       ↑               ↑          ↑
//                  collection        originalId   updated
```

由 `fetchCloudBackup` 在拉取数据时一并构建并返回。每条业务行都对应一个 `updated` 时间戳。

**示例：**

```jsonc
{
  "pb_tenants": {
    "tenant_001": "2026-04-21 09:30:12.345Z",
    "tenant_002": "2026-04-20 18:11:00.000Z"
  },
  "pb_units": {
    "u_a01": "2026-04-19 10:00:00.000Z"
  },
  "pb_yearly_targets": {
    "2026": "2026-01-01 00:00:00.000Z"   // 合成 key = year
  },
  "pb_monthly_init_data": {
    "2025_3": "2025-04-01 00:00:00.000Z" // 合成 key = year_month
  }
}
```

> **注意**：`pb_yearly_targets` 和 `pb_monthly_init_data` 没有 `original_id` 字段，
> RecordMeta 用「合成 key」识别（year / year_month）。`saveIncrementalToPocketBase`
> 内部的 `buildOriginalIdFilter` 会自动转换成正确的 PocketBase filter。

### 3.2 DirtyPayload —— DirtyTracker 提交结构

```ts
type DirtyPayload = Record<string, {
  creates: { originalId: string; data: Record<string, any> }[];
  updates: { originalId: string; changedFields: Record<string, any>; baseUpdated: string }[];
  deletes: { originalId: string; baseUpdated: string }[];
}>;
```

合并规则（详见 `services/dirtyTracker.ts` 头部注释，及单元测试）：

| 操作序列 | 提交结果 |
|---|---|
| 多次 update 同一行 | 字段合并，`baseUpdated` 取**最早一次** |
| create → update | 合并为单次 create |
| create → delete | 抵消，不发请求 |
| update → delete | 只剩 delete |
| delete → create | 视为复活，按 create 处理 |

### 3.3 IncrementalConflict —— 冲突结构

```ts
interface IncrementalConflict {
  collection: string;
  originalId: string;
  serverRecord: Record<string, any>;     // 服务端最新整条记录
  localChanges: Record<string, any> | null; // 本地试图写入的字段（delete 时为 null）
  baseUpdated: string;                   // 本地基准
  serverUpdated: string;                 // 服务端最新 updated
  op: 'update' | 'delete';
}
```

## 4 · 前端业务组件接入规范

### 4.1 读取 tracker

```tsx
import { useDirtyTracker } from '../services/dirtyTrackerContext';

const MyComponent = () => {
  const dt = useDirtyTracker();
  // dt 可能为 null：在 Provider 之外渲染时；做空值保护
  // ...
};
```

### 4.2 三类操作的标准模式

```tsx
const dt = useDirtyTracker();

// ① 修改既有租户的月租
const onChangeRent = (tenantId: string, newRent: number) => {
    setTenants(prev =>
        prev.map(t => t.id === tenantId ? { ...t, monthlyRent: newRent } : t)
    );
    dt?.tracker.markUpdate(
        'pb_tenants',
        tenantId,
        { monthly_rent: newRent },                    // ← PocketBase 字段名（snake_case）
        dt.getBaseUpdated('pb_tenants', tenantId),    // ← 加载时的 updated 时间戳
    );
};

// ② 新增租户
const onAddTenant = (newTenant: Tenant) => {
    setTenants(prev => [...prev, newTenant]);
    dt?.tracker.markCreate('pb_tenants', {
        id: newTenant.id,                  // 业务主键（必填）
        name: newTenant.name,
        monthly_rent: newTenant.monthlyRent,
        building_id: newTenant.buildingId,
        // ... 其它要写入 PB 的字段，按 snake_case 命名
    });
};

// ③ 删除租户
const onDeleteTenant = (tenantId: string) => {
    setTenants(prev => prev.filter(t => t.id !== tenantId));
    dt?.tracker.markDelete(
        'pb_tenants',
        tenantId,
        dt.getBaseUpdated('pb_tenants', tenantId),
    );
};
```

> **field 命名约定**：DirtyTracker 不做 camelCase ↔ snake_case 转换，组件传什么就发什么。
> 业务组件中应直接传 PocketBase 字段名（`monthly_rent`、`contact_info`、`building_id` 等）。
> 这意味着每个组件需要在「业务字段 → PB 字段」之间做一次显式映射。

### 4.3 平滑迁移策略

- 在所有业务组件接入完成前，应用默认运行在 `SAVE_MODE = legacy`，所有保存都走整包覆写，**与改造前完全一致**。
- 在测试环境设置 `VITE_SAVE_MODE=incremental` 灰度切换：
  - 已接入 tracker 的组件 → 走增量保存
  - 未接入 tracker 的组件 → `dirtyTracker.isEmpty()` → 自动 fallback 到 `saveToCloud` 并打印 `console.warn`，不会丢数据
- 待所有业务组件接入完成、回归测试通过后，把默认值改为 `incremental`，旧 `saveToPocketBase` 标记 `@deprecated` 但保留作为「全量覆盖」的强制入口。

## 5 · 冲突处理流程

```
用户点保存
   │
   ▼
saveIncrementalToCloud → 返回 conflicts[]
   │
   ▼
App 把 conflicts 写入 pendingConflicts state → ConflictDialog 渲染
   │
   ▼
用户为每条冲突选择 mine / theirs / skip → 点「应用决策」
   │
   ▼
handleResolveConflict(decisions[]) {
    for (mine 类) → forceOverwriteCloudRecord(...)  // 直接 PATCH，绕过 updated 比对
    theirs / skip → 服务端不变
    fetchCloudBackup → 刷新 recordMeta
    dirtyTracker.reset()
}
```

`ConflictDialog` 关键 UI 行为：
- 同一弹窗里展示**所有冲突**，每条独立选择
- 顶部「全部用服务端 / 全部用我的 / 全部跳过」批量按钮
- 字段级 diff：左列「我的值」（绿色），右列「服务端最新值」（蓝色）
- 默认动作 = 跳过（最安全，不会误覆盖）
- 删除冲突独立呈现：本地想删 vs 服务端被改

## 6 · 灰度回滚

| 环境变量 | 取值 | 含义 |
|---|---|---|
| `VITE_SAVE_MODE` | `legacy`（默认） | 完全沿用旧的整包覆写，零回归 |
| `VITE_SAVE_MODE` | `incremental` | 启用增量保存；未接入 tracker 的页面会 fallback + warn |

**回滚流程**（线上故障时）：
1. 在部署平台把 `VITE_SAVE_MODE` 改成 `legacy`
2. 重新构建/发布前端
3. 完全恢复改造前的行为；后端 `pb_billing_period_notes/dashboard_data_version` 仍正常维护

新增的 `saveIncrementalToPocketBase` / `forceOverwriteRecord` / `bumpCloudSaveVersion` 只在 `incremental` 模式下被调用，关闭后即"沉默"，不影响线上。
